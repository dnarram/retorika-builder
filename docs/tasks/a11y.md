## Objective

`a11y-size` stops being a weight check wearing an accessibility name: contrast and horizontal
overflow are verified on real rendered output, for every preset, every variant and every palette.

## Where it comes from

- Protocol Part 8.5: axe-core over every catalog preset and every variant, AA contrast minimum,
  and horizontal overflow checked at 320, 768 and 1280 pixels.
- Protocol Part 9.2: the `a11y-size` job, which today runs `pnpm size` and nothing else. The
  README says so in as many words, so that its green tick is not read as more than it is.
- Advanced dossier §4: *"antes de publicar, una revisión avisa de contraste insuficiente o de
  desbordes por debajo de 320 píxeles"*. The harness is the engine of a product feature, not
  housekeeping.

**Part 8.5 has been amended for this task.** Its original wording asked for every preset "en
claro y en oscuro", which cannot be followed: a document carries exactly one theme and there is
no dark concept in the model. The amended wording, now in the protocol, is **every preset, every
variant and every palette in `packages/tokens`** — contrast is a property of the palette, and a
dark palette is simply another palette.

## Why a real browser, and why only here

Both requirements need computed styles.

Overflow needs layout: happy-dom does not lay out, so an element's rendered width is not
something it can answer. And axe's contrast rule needs resolved colours — under happy-dom it
either skips or reports green without having compared anything.

**That second case is the dangerous one.** A contrast rule that silently passes is a guard with a
success path that checks nothing, which is the exact failure class this project has already
fixed three times in CI. A guard that cannot do its job must say so, not go green.

So Playwright enters scope, **for this task only**: Chromium alone, headless, two workers
locally per Part 18. There is still **no `e2e` job** and no browser flow test — that arrives with
the flows it is meant to exercise.

## Invariants it touches

**None of the five directly.** This task adds guards of its own rather than changing document
behaviour.

It is adjacent to `INV_5`: the harness renders published output, so if it ever disagrees with
`pnpm test:golden` about what a document produces, the golden corpus is right and the harness is
wrong.

## Steps

### 1. Dependencies

Add to the root `package.json` `devDependencies`: `@playwright/test`, `axe-core`, and
`@axe-core/playwright`. Pin them exactly, per ADR 0005, and record the date they were checked
against the registry in the commit message.

**Install Chromium only:** `pnpm exec playwright install --with-deps chromium`. No Firefox, no
WebKit. The browser is an implementation detail of two assertions, not a compatibility matrix.

### 2. `packages/renderer/test/browser-fixtures.ts`

```ts
import type { RetorikaDocument } from "@retorika/schema";

export interface Combination {
  /** Stable, human-readable: "cover/image-right/palette-calido". */
  id: string;
  catalogId: string;
  variantId: string;
  paletteId: string;
  document: RetorikaDocument;
}

/** Every preset x every variant x every palette. This is the amended Part 8.5, as code. */
export function allCombinations(): Combination[];
```

Build each document from a corpus fixture, swapping in `buildTheme({ paletteId, typePairId })`
from `@retorika/tokens` and the preset and variant under test. Every document must pass
`parseDocument` before it is used — a combination that is not a valid document is a bug in the
generator, not a finding.

The `id` is what a failure message prints. Make it identify the case without further digging.

### 3. `packages/renderer/test/a11y.browser.test.ts`

For each combination: `render(document, "html")`, load the HTML into a Chromium page via
`page.setContent`, and run axe with `@axe-core/playwright`.

- Fail on any violation of **impact `serious` or `critical`**, and on **any** violation of the
  `color-contrast` rule regardless of impact.
- The failure message names the combination id, the rule id, and the offending selector.
- **Assert the contrast rule actually ran.** Read axe's results and fail if `color-contrast`
  appears in neither `passes` nor `violations` — a rule that was skipped must not be mistaken for
  a rule that passed. This assertion is the reason a browser is here at all.

### 4. `packages/renderer/test/overflow.browser.test.ts`

For each combination, at viewport widths **320, 768 and 1280**:

- Assert `document.documentElement.scrollWidth <= window.innerWidth`.
- Assert no element's bounding box extends past the viewport's right edge.
- The failure message names the combination, the width, and the selector of the first offender.

320 is the number the dossier promises, so it is not negotiable downward.

### 5. `vitest.config.ts` and the script

Add an `"a11y"` project scoped to `*.browser.test.ts`, and exclude those files from the existing
`renderer` project so `pnpm test` does not silently require a browser.

Add `"test:a11y"` to the root `package.json`. Every job runs a named script — no command lives
only in the workflow.

Set two workers locally, per Part 18.

### 6. `.github/workflows/ci.yml`

In the `a11y-size` job, after the existing `pnpm size` step:

- install Chromium (`pnpm exec playwright install --with-deps chromium`), cached on the
  Playwright version;
- run `pnpm test:a11y`;
- raise `timeout-minutes` to a realistic figure — a browser download plus the matrix is not a
  ten-minute job.

**Delete the comment in that job that says it is weight-only**, and the matching caveat in the
README. Leaving them is how documentation starts lying.

### 7. Documentation

Update the README's `a11y-size` row to say what it now checks, and remove the "weight budget
only" warning. The `docs/protocolo.md` Part 8.5 amendment is already in place; confirm the file
matches what this task built.

## Out of scope

- **The `e2e` job and any Playwright flow test.** Browser access here buys exactly two
  assertions.
- Firefox and WebKit.
- Lighthouse.
- Any change under `packages/renderer/src/` or `packages/tokens/src/`.
- Auto-fixing findings, or a "suggested contrast" helper.
- Screenshot or visual-regression testing.
- Running the browser suites inside `pnpm test`; they stay a separate project so the default
  suite needs no browser.
- axe rules beyond serious/critical plus contrast. Widening the net is its own decision.

## If anything is unclear, stop and ask

The executor may **not** decide any of the following.

1. **A real violation in an existing preset, variant or palette.** The first run of a new
   contrast harness normally finds something genuine. If axe reports a real violation anywhere,
   **stop and report it**. Do not disable the rule, do not exclude the combination, do not adjust
   token values, and do not touch anything in `packages/renderer` to make it pass. A harness
   tuned until it goes green is a guard with a silent success path — the exact thing this task
   exists to remove. Bring the finding: which combination, which rule, which element, which
   measured ratio.
2. **The same for an overflow finding at 320.** It means a real section breaks on a real phone.
   That is a renderer fix, in an exclusive zone, in its own task.
3. **Raising the axe threshold above serious/critical**, or narrowing the palette matrix because
   it is slow. Slowness is a conversation about the matrix, not a reason to check less.
4. **Whether `packages/renderer` may be edited.** It may not, beyond devDependencies and test
   files. If a finding seems to require it, that is finding number 1 again.
